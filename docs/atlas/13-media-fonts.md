## 2. Big picture

### 2.1 What this area is

Two unrelated clusters that share the "generated data plus tools" style:

1. **Media decoding, all in ring 3 and all header-only.** `inflate.h`, `png.h`, `jpeg.h` and `svg.h` are `static inline` code included directly into each user program that needs them. Each `userland/*.c` is compiled as its own standalone ELF (`userland/build.sh:25-37`), so there is no shared library. The only production consumer is the browser (`userland/browser.c:36-38`); `inflate.h` is also used by `userland/fetch.h` for HTTP `Content-Encoding: gzip`. There is no image decoding in the kernel, and no encoder of any kind in zelr. All three decoders return the same `picture` type: `{int w, h; u8 *rgb;}` (`png.h:45-48`), which is always 3 bytes per pixel in R,G,B order, top-down, and allocated with `malloc` from `userland/alloc.h`.

2. **Text-rendering data.** There are two fonts:
   * An **8x16 1-bit bitmap font** of 95 glyphs (ASCII 32..126), hand-drawn as text art in `tools/genfont.py`. It is emitted twice: `kernel/font.c` for the kernel and `userland/font.h` for ring 3. The kernel uses it for the boot console (`kernel/fbcon.c:51-65`), the crash screen (`kernel/blackbox.c:177,188`), the kernel "about" window (`kernel/apps.c:26-58`) and a self-test. In ring 3 only `settings.c` still draws with it (`draw.h` `text()`).
   * An **anti-aliased outline typeface** defined procedurally in `tools/genface.py`. The outlines use a 1000-unit em built from `stem`, `bar`, `ring`, `diag` and `dot` primitives. They are rasterised at build time into 8-bit coverage bitmaps at fixed pixel sizes and emitted as three C headers. The kernel's window manager draws all chrome text with `include/face.h` through `kernel/gfx.c:261-337`. Ring-3 programs use `userland/face.h` through `userland/draw.h:127-231`. The browser lays out and draws page text with `userland/facetext.h` through `userland/layout.h:103-153` and `userland/browser.c:1035-1058`.

### 2.2 Design decisions and the reasons the comments give

* **Everything is written from the specification, and nothing is imported.** RFC 1951 for inflate (`inflate.h:6`), the PNG and JPEG specs (`png.h:6`, `jpeg.h:6`). The typeface is drawn in code: "Nothing is imported and nothing is traced" (`genface.py:17`). The 8x16 font used to be rendered from Consolas through PIL. It was replaced by hand-drawn art so that "the shapes are the project's own" (`genfont.py:4-8`).
* **Inflate is mandatory.** "a browser that cannot do this cannot show a picture at all" (`inflate.h:7-9`). The same inflate later served HTTP gzip (`fetch.h:137-150`): "Three to five times less to move".
* **Checksums are not verified.** zlib Adler-32 (`inflate.h:310-313`), gzip CRC-32 (`fetch.h:142-145`) and PNG chunk CRCs (never read) are all skipped. The stated reason is "what it would catch -- a corrupted download -- the transport has already checked, and a picture that decodes is a picture."
* **Output is always RGB888 with no alpha.** "carrying an alpha channel through the layout for the few images that have one would mean every drawing path had to know about it". Transparent PNG pixels are composited onto `bg` at decode time (`png.h:40-44`, `112-115`).
* **Refuse by name rather than decode wrongly.** This covers interlaced and 16-bit PNG (`png.h:27-30`), and progressive, arithmetic-coded and 12-bit JPEG (`jpeg.h:33-36`).
* **Partial output.** `inf_run` reports how much came out even on `INF_FULL`, because "A page read down to where the room ran out is worth more than no page". Images must not use that, because "half a PNG is not half a picture" (`inflate.h:267-278`).
* **The JPEG IDCT is the textbook formula in float.** It is not a fast factorisation, so that it stays readable (`jpeg.h:170-180`). The cosine table comes from a Taylor series because "there is no cosine in this system to ask" (`jpeg.h:187-189`). Ring-3 programs are built without `-mno-sse` (`userland/build.sh:27-35`), unlike the kernel (`build.sh:45`), so float and double are legal here.
* **SVG is a renderer, not a decoder** (`svg.h:8-18`). The motivation was the Google logo. Unsupported features are "skipped rather than approximated", except gradients (see drift §10). Curves are flattened (16 steps per cubic). The fill is a scanline with 4 sub-scanlines per pixel and exact horizontal span coverage.
* **The typeface is rasterised at build time, not on the machine,** because "a kernel that rasterises outlines needs floating point and a scanline filler in it" (`genface.py:931-936`).
* **The set of sizes follows the consumer** (`genface.py:938-983`). The kernel chooses its own sizes, so few are needed. Ring-3 chrome is "short on purpose" because every program that draws text carries the table. The browser gets 33 faces "close enough together that rounding to the nearest is not visible", in a separate header because it is "half a megabyte of coverage, and a calculator has no business carrying that around" (`genface.py:972-973`).
* **Bold is the same drawing with heavier `STEM`/`THIN`** (`genface.py:41-49`), not a second outline set.
* **Monospaced faces are derived from the proportional one** by condensing wide glyphs and centring narrow ones into a 620-unit cell (`genface.py:988-1012`), so that "column n is under column n on the line above".
* **Contours are unioned with max(), not with a global even-odd pass.** With an even-odd pass, overlapping strokes such as the H crossbar over its stems cancel (`genface.py:196-203`).

## 3. File-by-file detail

### 3.1 `userland/inflate.h` -- DEFLATE and zlib

Includes `zelr.h` only. It has no allocation of its own: the caller provides the output buffer.

**Return codes** (`inflate.h:28-31`):

| Code | Value | Meaning |
|---|---:|---|
| `INF_OK` | 0 | Success. |
| `INF_TRUNCATED` | -1 | The input ended in the middle of something. |
| `INF_FULL` | -2 | There was more output than room for it. |
| `INF_BAD` | -3 | The input does not decode (not deflate, or damaged). |

**Constants:** `INF_SYMS 288` (`:34`) is the largest alphabet size.

**Types**
* `inf_huff` (`:36-39`) is a canonical Huffman table in the style of zlib's reference decoder `puff`:
  * `short count[16]` holds the number of codes of each length. `count[0]` counts unused symbols.
  * `short symbol[288]` holds the symbols sorted by code.
* `inf_state` (`:41-51`):
  * `in`, `n`, `at`: the input buffer, its length, and the read position.
  * `u32 bits`, `int nbits`: the LSB-first bit reservoir.
  * `out`, `cap`, `len`: the flat output buffer, which also serves as the history window.
  * `err`: a sticky error code.

**Functions**
* `inf_bits(s, need)` (`:57-67`) reads bits LSB-first, pulling one byte at a time. On underrun it sets `err=INF_TRUNCATED` and returns 0. After each call `nbits` is always in 0..7, which is what lets `inf_stored` discard "the rest of the current byte" safely. `need=0` returns 0 without reading.
* `inf_build(h, len, n)` (`:76-99`) counts code lengths. If every length is 0 it returns OK with an empty table; the comment says this is legal, for example for "no distances". It rejects over-subscribed codes (`left<0`, giving `INF_BAD`) and fills `symbol[]` by length offset. It does **not** reject incomplete (under-subscribed) codes, although the comment at `:84-85` says those are "legal only for the one code case".
* `inf_decode(s, h)` (`:101-115`) is the bit-serial canonical decode. For length 1..15 it shifts in one bit and tests `code - count < first`. After 15 bits it sets `INF_BAD`. On an empty table this safely ends in `INF_BAD`.
* Fixed tables (`:119-134`): `INF_LEN_BASE[29]` and `INF_LEN_EXTRA[29]` (lengths 3..258), `INF_DIST_BASE[30]` and `INF_DIST_EXTRA[30]` (distances 1..32768).
* `inf_block(s, lit, dist)` (`:146-174`) is the symbol loop:
  * Symbols below 256 are literals. Output is checked against `cap`, giving `INF_FULL`.
  * 256 ends the block.
  * 257..285 are length codes; above that is `INF_BAD`.
  * A distance must satisfy `back <= len`, otherwise `INF_BAD`. There is no preset dictionary and no separate 32 KB window: the whole output buffer is the window.
  * The copy is byte-by-byte on purpose, because overlapping copies (distance shorter than length) encode runs (`:142-145`).
  * **Error bug:** at `:163-164`, `if (s->err || dsym < 0 || dsym >= 30) s->err = INF_BAD`. This overwrites an `INF_TRUNCATED` raised while reading the length's extra bits or the distance code. See §10.
* `inf_fixed` (`:178-195`) rebuilds the fixed lit/len table (lengths 8/9/7/8) and the 30 five-bit distance codes on every fixed block.
* `inf_dynamic` (`:197-249`):
  * Reads HLIT+257, HDIST+1 and HCLEN+4. It rejects `nlen>286 || ndist>30`.
  * Reads the code-length code lengths in the RFC `ORDER[19]` (`:206-208`).
  * Decodes code lengths with repeat codes 16 (previous length ×3..6; `at==0` is `INF_BAD`), 17 (zeros ×3..10) and 18 (zeros ×11..138). Overrunning `nlen+ndist` is `INF_BAD`. Repeats may cross from the literal/length lengths into the distance lengths, which is correct.
  * It does not check that symbol 256 has a nonzero length; `puff` does.
* `inf_stored` (`:251-265`) discards the bit buffer, reads LEN/NLEN, requires `LEN == ~NLEN`, then copies bytes.
* `inf_run(in, n, out, cap, &out_len)` (`:279-301`) is the block loop, reading 1 bit BFINAL and 2 bits BTYPE per block. BTYPE 3 is `INF_BAD`. It always writes `*out_len`, including on error. Data after the final block is ignored.
* `inflate_raw(in, n, out, cap)` (`:304-308`) returns the byte count or a negative `INF_*`. Any error, including `INF_FULL`, is a failure.
* `inflate_zlib(in, n, out, cap)` (`:314-323`) checks the 2-byte header: CM must be 8, `(CMF<<8|FLG) % 31 == 0`, and FDICT must be clear. CINFO is ignored. It then calls `inflate_raw(in+2, n-2, …)`. The Adler-32 trailer is ignored.

**The gzip wrapper is not in this file.** It is `wh_gunzip` in `userland/fetch.h:151-182`:
1. Requires `len>=12` and magic `1F 8B 08`.
2. Skips FEXTRA, FNAME, FCOMMENT and FHCRC.
3. `malloc(cap)`s a temporary buffer and calls `inf_run` directly.
4. Accepts `INF_FULL` as a success that sets `*cut=1`.
5. Copies the output back over `body`.

Only one gzip member is decoded, and the CRC-32 and ISIZE fields are ignored.

**Performance character:** decoding is bit-at-a-time with no lookup tables, and the fixed tables are rebuilt per block. It is simple and slow, which the design accepts.

### 3.2 `userland/png.h` -- PNG decoder

Includes `zelr.h`, `alloc.h` and `inflate.h`.

* **Codes** (`:33-38`): `PNG_OK 0`, `PNG_NOT_PNG -1`, `PNG_TRUNCATED -2`, `PNG_UNSUPPORTED -3`, `PNG_TOO_BIG -4`, `PNG_BAD -5`.
* **Limits** (`:51-52`): `PNG_MAX_SIDE 4096` and `PNG_MAX_PIXELS 16*1024*1024`. The pixel test `w*h > PNG_MAX_PIXELS` at `:157` can never fire, because 4096² equals `PNG_MAX_PIXELS` exactly.
* **Helpers:** `png_be32` (`:54-56`) and `png_is(p, "NAME")` (`:58-61`).
* **Filters:**
  * `png_paeth(a, b, c)` (`:70-77`) breaks ties in spec order a, then b, then c.
  * `png_unfilter(row, prev, len, bpp, filter)` (`:79-108`) handles None, Sub, Up, Average (floor `(left+up)>>1`) and Paeth, in place from left to right. `prev == 0` means the first row, where up is 0. An unknown filter byte (>4) is silently treated as None.
  * `bpp` is 1 for sub-byte depths, as the comment at `:65-69` insists.

**`png_decode(data, n, out, bg)`** (`:116-291`):

1. Sets `out` to empty. Checks the 8-byte signature: fewer than 8 bytes gives `PNG_TRUNCATED`, a mismatch gives `PNG_NOT_PNG`.
2. `zdata = malloc(n)`. The IDAT concatenation can never exceed the input size (`:131-133`).
3. The chunk loop `while (at + 8 <= n)` (`:142-185`) has a bounds check `clen > (u32)(n - at - 12)` that yields `PNG_TRUNCATED`. That check is **unsafe when 8 ≤ n−at < 12**; see §10.
   * **IHDR** (`clen>=13`): reads w, h, depth, colour and interlace.
     * `w/h <= 0` or over the limits gives `PNG_TOO_BIG`.
     * `interlace != 0` gives `PNG_UNSUPPORTED`.
     * `depth == 16` gives `PNG_UNSUPPORTED`.
     * A depth other than 1, 2, 4 or 8 gives `PNG_BAD`.
     * A colour type other than 0, 2, 3, 4 or 6 gives `PNG_BAD`.
     * `depth != 8 && colour not in {0, 3}` gives `PNG_UNSUPPORTED`. Those combinations are invalid PNG anyway.
     * The compression and filter method bytes (`body[10..11]`) are not checked.
   * **PLTE:** up to 256 entries.
   * **tRNS:** up to 256 bytes copied into `trans[]` (default 255). It is only *applied* for colour type 3. Colour-key tRNS for types 0 and 2 is ignored.
   * **IDAT:** appended to `zdata`, capped at `n`.
   * **IEND:** stops the loop. All other chunks (gAMA, cHRM, sRGB, iCCP, pHYs, text chunks and so on) are skipped, and CRCs are never read. Gamma is therefore ignored.
4. No IHDR gives `PNG_BAD`. No IDAT data gives `PNG_TRUNCATED`.
5. The channel count is 1, 3, 1, 2 or 4 for colour types 0, 2, 3, 4 and 6. Then `stride = ceil(w*channels*depth/8)` and `raw_len = (stride+1)*h`.
6. `inflate_zlib(zdata, zlen, raw, raw_len)`. `INF_TRUNCATED` maps to `PNG_TRUNCATED`; every other error, including `INF_FULL`, maps to `PNG_BAD`.
7. `rgb = malloc(w*h*3)`. For each row:
   * If the inflated data ended early (`off+stride+1 > got`), the remaining rows are filled with `bg` and the loop stops (`:221-230`). This only happens when inflate *succeeded* with short output. A truncated stream is an error, not a partial picture.
   * Otherwise the row is unfiltered, then pixels are converted:
     * Depth 8: grey, RGB, palette (an index ≥ `palette_n` gives black, alpha from `trans`), grey+alpha, RGBA.
     * Sub-byte depths: packed MSB-first; palette as above, or grey scaled `idx*255/max`.
   * Alpha is composited in integers: `(c*a + bg*(255-a))/255` (`:274-276`).
8. Frees `raw` and `zdata`, fills `out`, returns `PNG_OK`. Every error path frees what it allocated; this is verified by `pngtest.c:184-194`.

* `picture_free(p)` (`:293-297`) frees `p->rgb` and zeroes the struct.
* `png_why(rc)` (`:299-307`) gives human-readable strings. **It is never called anywhere.** `jpeg_why` and `svg_why` are likewise unused.

**Memory:** the peak is roughly `n` (zdata) + `raw_len` + `w*h*3`. For a 4096×4096 RGBA image that is about 67 MB + 48 MB, and in that case `malloc` would likely fail, returning `PNG_TOO_BIG`.

### 3.3 `userland/jpeg.h` -- JPEG decoder

Includes `zelr.h`, `alloc.h` and `png.h` (for `picture`, which also pulls in `inflate.h`).

* **Codes** (`:39-45`): `JPG_OK 0`, `JPG_NOT_JPEG -1`, `JPG_TRUNCATED -2`, `JPG_PROGRESSIVE -3`, `JPG_UNSUPPORTED -4`, `JPG_TOO_BIG -5`, `JPG_BAD -6`.
* **Limits** (`:47-49`): `JPG_MAX_SIDE 8192`, `JPG_MAX_PIXELS 24*1024*1024`, `JPG_COMPONENTS 4` (array size; only 1 or 3 are accepted).
* `JPG_ZIGZAG[64]` (`:54-63`) maps zigzag index to natural index. It is correct.

**Types**
* `jhuff` (`:65-70`): `u8 bits[17]`, `u8 vals[256]`, `int mincode[17]`, `maxcode[18]`, `valptr[17]`, `int present`.
* `jcomp` (`:72-78`):
  * `id`, `h`, `v`: sampling factors, each 1..4.
  * `tq`: the quantisation table index.
  * `td`, `ta`: the DC and AC Huffman table indices, set by SOS.
  * `dc`: the DC predictor.
  * `u8 *pix`: the component plane.
  * `bw`, `bh`: the plane size in blocks.
* `jstate` (`:80-97`):
  * `in`, `n`, `at`; `u32 bits`, `nbits`; `marker_hit`.
  * `u16 quant[4][64]`, initialised to 1.
  * `jhuff hdc[4], hac[4]`.
  * `w`, `h`, `ncomp`, `comp[4]`, `hmax`, `vmax` (initialised to 1), `restart`, `err`.
  * It lives on the stack, about 4.5 KB.

**Bits and Huffman**
* `jpg_bit` (`:105-119`) reads MSB-first.
  * `FF 00` is byte stuffing: the `00` is skipped.
  * `FF` followed by anything else sets `marker_hit=1`, backs `at` up to the `FF` and feeds zero bits from then on.
  * A trailing `FF` at end of input is treated as if followed by `D9`.
  * Running off the end gives `JPG_TRUNCATED`.
  * `marker_hit` is set and cleared but never checked.
* `jpg_bits` (`:121-125`) and `jpg_extend` (`:131-134`) do the JPEG sign extension.
* `jpg_huff_build` (`:141-154`) is the JPEG Annex F.2.2.3 table build (`mincode`, `maxcode`, `valptr`; a length with no codes gets `maxcode=-1`).
* `jpg_decode` (`:156-168`) is the bit-serial decode up to 16 bits. A missing table (`present==0`) or no match gives `JPG_BAD`.

**IDCT**
* `static float JPG_COS[8][8]` and `JPG_COS_READY` (`:181-182`) form a process-global table initialised lazily.
* `jpg_cos_init` (`:184-219`) computes `cos((2x+1)uπ/16)` as a double Taylor series with 11 terms, after reducing the angle into [−π, π]. The comment `:194-203` records the bug this fixed: without the reduction, the series at 20 rad produced noise for every frequency above the first two. The table is pre-scaled by `1/√8` for u=0 and `1/2` otherwise.
* `jpg_idct(in, out, stride)` (`:221-247`) is a separable 8-point IDCT in float, rows then columns, about 1024 multiply-adds per block. It adds the level shift and rounds with `(int)(sum + 128.5f)`, then clamps to 0..255.

**Blocks and scan**
* `jpg_block` (`:250-283`) decodes one block:
  * DC: size, then bits, `dc += diff`, `coef[0] = dc*q[0]`.
  * AC: (run, size) symbols. EOB is (0,0). ZRL (15,0) adds 16 to `k`. `k>63` breaks.
  * Dequantisation is `coef[ZIGZAG[k]] = val * q[k]`, with the quantisation table kept in zigzag order as it arrives in DQT.
  * Then the IDCT straight into the component plane.
* `jpg_scan` (`:288-337`):
  * MCU grid `mcux = ceil(w/(8*hmax))`, `mcuy = ceil(h/(8*vmax))`.
  * **Restart handling:** when `restart` is set and `since_restart == restart`, it drops the bit buffer, scans forward to the next `FF D0..D7` (it does not check the RST sequence number) and resets all DC predictors.
  * Each MCU decodes, for each component in frame order, `v×h` blocks.
  * The `waste` branch (`:320-324`) is unreachable, because planes are sized to whole MCUs.

**`jpeg_decode(data, n, out)`** (`:340-546`):

1. Fewer than 4 bytes gives `JPG_TRUNCATED`. A file not starting `FF D8` gives `JPG_NOT_JPEG`. Calls `jpg_cos_init()`.
2. The marker loop `while (at+3 < n)` (`:366-484`):
   * It skips non-`FF` bytes.
   * SOI, TEM (`01`) and RST0-7 are skipped. EOI breaks the loop.
   * All other markers read a 16-bit length; a bad length gives `JPG_TRUNCATED`.
   * **`FF` fill bytes before a marker are not handled** (see §10).
   * **SOF0 / SOF1** (`C0`, `C1`):
     * Precision must be 8, otherwise `JPG_UNSUPPORTED`.
     * Size limits apply (`JPG_TOO_BIG`).
     * `ncomp` must be 1 or 3, otherwise `JPG_UNSUPPORTED`. This excludes CMYK and YCCK.
     * Sampling factors must be 1..4.
     * Each plane is `(mcux*h*8)×(mcuy*v*8)` bytes, filled with 128.
   * **SOF2** gives `JPG_PROGRESSIVE`.
   * **SOF9/10/11** (arithmetic coding) give `JPG_UNSUPPORTED`.
   * SOF3, SOF5-7 and SOF13-15 are not recognised. They are skipped like any other segment, and then SOS fails with `JPG_BAD` because `w == 0`.
   * **DHT** (`C4`): several tables per segment; `th>3` gives `JPG_BAD`; no more than 256 values.
   * **DQT** (`DB`): 8-bit and 16-bit tables are both accepted; `tq>3` gives `JPG_BAD`.
   * **DRI** (`DD`): sets the restart interval.
   * **SOS** (`DA`):
     * No SOF yet gives `JPG_BAD`.
     * `ns != ncomp` gives `JPG_UNSUPPORTED`. Only a single interleaved scan is supported.
     * It maps each component selector to td/ta by component id. Ss, Se, Ah and Al are ignored.
     * Then `jpg_scan`, then `goto done`. Only the first scan is decoded.
   * APPn (including EXIF and Adobe APP14) and COM are skipped. There is no EXIF orientation and no Adobe colour-transform handling.
3. If no scan was decoded, or any error occurred, the planes are freed. `JPG_OK` without a scan becomes `JPG_TRUNCATED`.
4. Output conversion:
   * Greyscale: Y.
   * Colour: nearest-neighbour upsampling of each plane by `(y*c->v/vmax, x*c->h/hmax)`, then fixed-point YCbCr to RGB: `R = Y + 1436·Cr>>10`, `G = Y − 352·Cb>>10 − 731·Cr>>10`, `B = Y + 1815·Cb>>10`. That is ×1024 of 1.402, 0.344, 0.714 and 1.772. Results are clamped.
   * Any h/v combination works for interleaved scans: 4:2:0, 4:2:2, 4:4:4, 4:1:1 and so on.
5. **Single-component files with sampling factors ≠ 1×1** are decoded with interleaved MCU order. The spec says a one-component scan is non-interleaved, one block per MCU in raster order, so such files come out scrambled. This is rare in practice; see §10.
6. `jpeg_why(rc)` (`:548-557`) is unused.

### 3.4 `userland/svg.h` -- SVG renderer

Includes `zelr.h`, `alloc.h`, `dom.h` (the HTML parser: `ddoc`, `dom_parse`, `dom_attr`, `dom_attr_fold`, `dom_next`, `dom_tag_name`), `png.h` (`picture`) and `css.h` (`css_color`).

* **Codes** (`:46-49`): `SVG_OK 0`, `SVG_NOT_SVG -1`, `SVG_TOO_BIG -2` (also returned for allocation failure and for w or h below 1), `SVG_NOTHING_IN_IT -3`.
* **Limits** (`:51-54`): `SVG_MAX_PTS 16384` flattened points per path (extra points are dropped silently), `SVG_MAX_SUB 256` subpaths (extras merge into the last one), `SVG_MAX_SIDE 2048` (the output size is clamped, not refused), `SVG_SUB 4` sub-scanlines.
* **Types:**
  * `svpt {float x, y}`.
  * `svmat {a, b, c, d, e, f}`, affine with `x' = a·x + c·y + e`, `y' = b·x + d·y + f`.
  * `svpath {svpt pts[16384]; int n; int start[256]; int nsub;}`, about 132 KB. It must never be placed on the stack (`:323-331`).
  * `svcanvas {u8 *rgb; int w, h;}`.
* **Matrix helpers:** `sv_identity`, `sv_mul(x, y)` (x then y applied innermost: `x·y`), `sv_apply` (`:71-92`).
* **Number reader:**
  * `sv_space` treats space, comma, tab, CR and LF as separators.
  * `sv_number(&p)` handles sign, integer part, fraction and exponent (clamped to 30 steps). It is float and not correctly rounded.
  * `sv_more` asks whether another number follows.
  * `"10-20"` parses as two numbers. Compact arc flags such as `"00"` would parse as a single number.
* **Path building:** `sv_begin` starts a subpath (up to 256). `sv_add` transforms and appends a point. `sv_cubic` flattens with 16 fixed steps (`:161-174`).
* **`sv_path_data(path, m, d)`** (`:178-293`) handles:
  * M/m. An implicit repeat after M is treated as L.
  * L, H and V.
  * C and S. S reflects the previous control point whenever `have_control` is set, even if the previous command was a Q or T; strictly, the reflection should only follow C or S.
  * Q and T, converted to cubics with the 2/3 rule.
  * **A/a drawn as a straight chord** to the endpoint (`:269-284`).
  * Z adds the start point.
  * Relative forms of all of the above. Any unknown command stops the parse.
* **`sv_span(cov, w, x0, x1)`** (`:307-321`) adds exact fractional coverage for one sub-scanline span.
* **`sv_fill_pts(cv, pts, n, start, nsub, colour, evenodd, alpha)`** (`:333-427`):
  1. Takes the y bounding box and `malloc`s `w` floats of coverage.
  2. For each pixel row and each of 4 sub-scanlines at `y + (s+0.5)/4`, collects edge crossings across all subpaths into `xs[256]`/`dirs[256]` (capped at 250). Every subpath is implicitly closed.
  3. Insertion-sorts the crossings. Even-odd pairs them; nonzero accumulates winding.
  4. Pixel alpha is `cov/4·alpha`. Values at or below 0.002 are skipped. Blending is a float lerp over the existing RGB.
* `sv_fill` (`:429-433`) is a wrapper.
* **`sv_stroke(cv, path, colour, width, alpha)`** (`:439-474`):
  * Minimum width is 0.6.
  * For each consecutive pair of points within a subpath it fills a quad offset by the normal. The segment length comes from a Heron/Newton square root with 12 iterations.
  * There are no joins or caps, and no wrap from the last point back to the first.
* **`sv_paint(d, el, name, &out)`** (`:487-524`):
  * Reads the attribute first, and otherwise searches the `style` attribute for `name:` (case-folded).
  * `none` returns 0.
  * `url(...)` (a gradient or pattern) gives flat grey `0x9A9A9A`.
  * Anything else goes to `css_color`, which supports #rgb, #rrggbb, rgb()/rgba() and about 60 names. `transparent` maps to white (`css.h:231`).
* **`sv_attr_num`** (`:526-532`) reads the attribute only, never `style`, with units ignored.
* **`sv_transform(d, el, parent)`** (`:535-599`):
  * Supports `translate`, `scale`, `matrix` (6 numbers) and `rotate(deg [cx cy])`.
  * Rotation uses sin and cos from 10-term series after reducing to [−180, 180].
  * Transforms in a list are applied left to right (`m = m·t`).
  * `skewX`/`skewY` are ignored.
  * `translate()` or `scale()` with no numbers reads the uninitialised `a[0]`.
* **`sv_shape(d, el, m, path)`** (`:602-674`) handles:
  * `path` (from `d`).
  * `rect`: 4 points, no closing point, `rx`/`ry` ignored.
  * `circle`/`ellipse`: 4 cubics with k=0.5522847, and closed.
  * `line`.
  * `polygon`/`polyline` (from `points`, no closing point). The tag is matched case-insensitively.
* **`svg_render(xml, len, want_w, want_h, out, bg)`** (`:682-812`):
  1. `malloc(sizeof(ddoc))`, about 2.6 MB given `DOM_NODES 20000`, `DOM_ATTRS 40000` and `DOM_ARENA 1.5 MB` (`dom.h:37-39`), then `dom_parse`. The first element named `svg` is the root; if there is none, `SVG_NOT_SVG`.
  2. `viewBox` is read with `dom_attr_fold`, because the parser lower-cases attribute names (`svgtest.c:223-233`, `dom.h:214-234`).
  3. The output size is `want_*`, else the `width`/`height` attributes, else the viewBox size, else 100×100, clamped to 2048.
  4. The canvas is filled with `bg`. The base transform is uniform scale `min(w/vw, h/vh)`, centred (the xMidYMid meet default; `preserveAspectRatio` is ignored).
  5. `malloc(svpath)`.
  6. Every element in document order is visited with `dom_next`. For each one:
     * The transform chain is built from the element up to, but excluding, the root, at most 32 levels, relying on node indices increasing in document order. The root's own `transform` is not applied.
     * `sv_shape` builds the path.
     * **Fill:** if `sv_paint` gives no colour, no `fill` attribute exists, and the element is not a `line` or `polyline`, the fill defaults to black. This is how `style="fill:none"` wrongly becomes black; see §10.
     * `opacity` and `fill-opacity` are multiplied; `fill-rule="evenodd"` is honoured.
     * The stroke uses `stroke-width × sc` (the viewBox scale only) and `stroke-opacity × opacity`.
     * There is **no inheritance** of fill, stroke or opacity from ancestors such as `<g>`. There is **no skipping** of `<defs>`, `<clipPath>`, `<mask>`, `<symbol>`, `<pattern>` or `<marker>` subtrees. `<use>`, `<text>` and `<image>` are not drawn.
     * `depth` and `stack[32]` are dead (`:746-748`, `:800-801`).
  7. Frees `path` and `doc`. If nothing was drawn, frees `rgb` and returns `SVG_NOTHING_IN_IT`.
* `svg_why` (`:814-821`) is unused.

**Pen primitives** (`class Pen`, `:73-154`). Each builds closed contours, which are lists of points:
* `move`, `line`, `curve` (a quadratic flattened by `_bez` in 12 steps, `:61-70`), `close`, `_flush` (drops contours with 2 or fewer points).
* `stem(x, y0, y1, w=STEM)`: a vertical rectangle centred on x.
* `bar(x0, x1, y, h=THIN)`: a horizontal rectangle centred on y.
* `ring(cx, cy, rx, ry, w, a0=0, a1=360, steps=48)`: an arc band. The outer edge runs forward and the inner edge runs back, forming one polygon.
* `diag(x0, y0, x1, y1, w=STEM)`: a quad whose width is measured perpendicular to the stroke.
* `dot(cx, cy, r)`: a 30-gon.
* `_bowl(p, x0, x1, y0, y1, w, a0, a1)` (`:266-269`): a ring whose outer edge touches the box.
* (Cosmetic: the `stem`, `bar` and `diag` "docstrings" come after an `if` statement, so they are not docstrings.)

**Rasteriser** (`:157-246`):
* `SUB = 4`.
* `_coverage(edges, w, h, into)` walks 4 sub-scanlines per pixel row. For each it collects edge crossings (half-open `ay <= y < by`), sorts them, and pairs them even-odd. It adds exact horizontal coverage `covered × 255/4` per pixel.
* `rasterise(contours, px_size, pad=1)`:
  1. `scale = px/1000`.
  2. The bounding box is `x0 = int(minx·s) − 1`, `x1 = int(maxx·s) + 2`, and the same for y (y is flipped). `int()` truncates toward zero.
  3. Each contour is rasterised separately, and the results are merged with `max` (a union).
  4. Bytes are `min(255, int(v))`.
  5. It returns `(w, h, left=x0, top=y1, rows)`, where `top` is the number of pixels above the baseline at which the bitmap starts.
* There is **no hinting or grid fitting.** Verified by hand: the 13px `I` is `stem(150, 0, 700, 92)`, which gives x 1.352..2.548 px and y 0..9.1 px. * **`build(size, weight, mono)`** (`:1015-1031`) calls `set_weight` and returns one tuple `(w, h, left, top, advance, bytes)` per glyph. The advance is `round(adv·size/1000)`, or the mono step `round(620·size/1000)`. Python's `round()` rounds half to even.
  * Mono steps: 12→7, 13→8, 14→9, 15→9, 17→11.
  * Bold faces keep exactly the regular advances (verified: 0 of 95 differ between 15 and 15b).
* **`emit(path, guard, sizes, prefix, decls=True, include=None)`** (`:1034-1113`) writes:
  * The header comment, `#pragma once`, then `#include "types.h"` (when guard is set), `"zelr.h"`, or the given include.
  * If `decls`: the `face_glyph` typedef, `FACE_FIRST 32`, `FACE_LAST 126`, `FACE_COUNT 95`.
  * `<PREFIX>_SIZES n`.
  * For each face with tag `<size><b?><m?>`:
    * `static const unsigned char <prefix>_px_<tag>[N]` as decimal bytes, 24 per line.
    * `static const face_glyph <prefix>_g_<tag>[95]` as `{ w, h, left, top, advance, at }` with a character comment.
  * If `decls`: the `face_t` typedef.
  * `static const face_t <prefix>_faces[<PREFIX>_SIZES]`.
  * It opens the file with `newline=""`, so the output is LF on every host.
* **`main`** (`:1116-1170`):
  * `--mono [N]` renders the mono face as ASCII cells.
  * `--preview [--bold]` shows "Hamburgefonstiv 0123456789" at 22 px.
  * Otherwise it emits `include/face.h` (guard, `face`), `userland/face.h` (no guard, so `zelr.h`, `face`) and `userland/facetext.h` (guard, prefix `tface`, `decls=False`, `include="face.h"`).
  * Paths are relative, so run it from the repository root: `python tools/genface.py`.

**Determinism:** the output is pure Python with fixed ordering and no randomness. Values depend on IEEE double arithmetic and `math.cos`/`sin`/`hypot`; a 1-ulp libm difference on another platform could in principle change a truncated coverage byte by 1. The in-tree outputs are consistent with the current script:
* The advance tables of all 47 faces match the recomputation.
* The 13px `I` coverage matches a hand computation.
* The duplicated faces (13, 15, 20, 15b, 15m, 15bm) are byte-identical between `include/face.h` and `userland/face.h`. The shared ones (13, 15, 15b, 15m, 15bm) are also identical in `facetext.h`.

The script was not run, so this is strong but not complete evidence that the tree is regenerated.

### 3.10 The generated face headers

**Common layout:**

```c
typedef struct {            /* 16 bytes */
    short w, h;             /* bitmap size including 1px padding on each side */
    short left, top;        /* bitmap origin relative to pen x and baseline: col = x+left+gx, row = baseline-top+gy */
    short advance;          /* pen advance in px */
    unsigned int at;        /* offset of the bitmap in <prefix>_px_<tag> (row-major, w*h bytes) */
} face_glyph;
typedef struct { short size; short bold, mono; const face_glyph *glyphs; const unsigned char *pixels; } face_t;
```

* A glyph is found as `f->glyphs[c - FACE_FIRST]`, and its bitmap starts at `f->pixels + g->at`.
* Space has `w = h = 0`.
* Offsets are contiguous: `at[i+1] = at[i] + w[i]*h[i]`, and the last glyph ends exactly at the array size. This was verified for the 15px face.
* Coverage bytes run from 0 (background) to 255 (solid).

## 4. Control flow and lifecycles

### 4.1 Browser: picture fetch, decode and draw

`build()` calls `pics_drop()` and then, when `want_sheets` is set, `gather_pictures()` (`browser.c:784-786`, `710-767`):
1. For each `<img src>` (at most `PICS_MAX 24`, `browser.c:123`): `url_join`, then `web_get(&u, cssbuf, CSS_MAX /*512 KB*/, &r)`. Any error, status 400 or above, or an empty body counts as skipped.
2. The format is sniffed from the bytes, not the Content-Type:
   * `\x89PNG`: `png_decode(body, len, &pic, 0xFFFFFF)`.
   * `FF D8`: `jpeg_decode`.
   * A first non-whitespace byte of `<`: `svg_render(body, len, want_w, want_h, &pic, 0xFFFFFF)`, where `want_w/h = lay_number(img width/height)`.
3. On success the picture's size is recorded in `pic_sizes[]` (`limage`) for the layout.
4. Drawing (`browser.c:1082-1106`): for an `LK_IMAGE` item, the picture is scaled nearest-neighbour to the item's `w×h` and written into the XRGB surface.
5. `pics_drop()` calls `picture_free` on each picture (`browser.c:136-141`).

### 4.2 HTTP gzip body

1. The request header always carries `Accept-Encoding: gzip` (`fetch.h:529-533`).
2. After de-chunking (`fetch.h:676-682`), if `content-encoding` starts with "gzip", `room = cap - (body - buf) - 1` is computed and `wh_gunzip(body, len, room, &cut)` is called (`fetch.h:684-699`).
3. On failure: `web_drop()` and `WEB_ERR_ENCODING`. On `INF_FULL`: `r->truncated = 1`.
4. The output is NUL-terminated.

### 4.3 Decoders as step sequences

* PNG: §3.2 steps 1-8.
* JPEG: §3.3 (markers, then the single scan, then conversion).
* SVG: §3.4 `svg_render` steps 1-7.

Each decoder is a single synchronous call with no persistent state. The only exception is the lazily initialised `JPG_COS` table.

### 4.4 Inflate state machine

`inf_run` repeats the following until a block with BFINAL set completes, or until `err` becomes nonzero:
1. Read BFINAL and BTYPE.
2. BTYPE 0: `inf_stored`. BTYPE 1: `inf_fixed` then `inf_block`. BTYPE 2: `inf_dynamic` then `inf_block`. BTYPE 3: `INF_BAD`.

`err` is sticky, and every function returns as soon as it is set.

### 4.5 Text drawing (kernel window manager)

`wm.c` calls `face_text(x, y, s, colour, FACE_BODY / FACE_BODY_BOLD / FACE_SMALL / FACE_HEAD / FACE_HEAD_BOLD)` and centres vertically with `face_height(which)` (for example `wm.c:1652-1661`, `2703-2706`, `2817-2822`). It draws straight into the back buffer, which the framebuffer layer then flushes.

### 4.6 Regeneration workflow

The generators are not part of `build.sh`; their outputs are checked in. Run each from the repository root on a host with Python 3:
* `python tools/genfont.py` writes `kernel/font.c` and `userland/font.h`. `-p` prints a preview.
* `python tools/genface.py` writes `include/face.h`, `userland/face.h` and `userland/facetext.h`. It is slow, because it is pure Python rasterising 47 faces × 95 glyphs. `--preview [--bold]` and `--mono [N]` are the inspection modes.
* `python tools/genpng.py` writes `userland/pngdata.h`. It needs Python's `zlib`.
* `python tools/genjpeg.py` writes `userland/jpegdata.h`. It needs Windows PowerShell with System.Drawing.

Then rebuild with `bash build.sh`, which builds userland first and embeds the test ELFs through `kernel/builtin.S`.

## 6. Concurrency, locking, memory ownership and invariants

* **Threading:** ring-3 programs are single-threaded (`alloc.h:19-20`). The decoders are reentrant apart from the lazy global `JPG_COS` / `JPG_COS_READY` (`jpeg.h:181-218`), which is idempotent and would only race if threads existed. Kernel drawing runs under the kernel's global locking. The face data is `const` (`.rodata`) and never written.
* **Ownership:**
  * On success, a decoder hands the caller `picture.rgb` from `malloc`; the caller frees it with `picture_free`.
  * On any failure, `out->rgb == 0` and nothing needs freeing. The refusal tests assert this.
  * Internal temporaries (`zdata`, `raw`, component planes, `ddoc`, `svpath`, per-fill `cov`) are freed on every path. The leak tests assert `heap_live()` does not grow.
  * `inflate.h` never allocates. `wh_gunzip` allocates and frees a temporary of `cap` bytes.
* **Stack discipline:** an `svpath` (132 KB) must never be on the stack (`svg.h:323-331`); strokes build a 4-point quad on the stack instead. The user stack now grows on demand up to `USER_STACK_MAX` of 1 MB (`include/user.h:104`, `kernel/user.c:306-319`). The stated 64 KB reason is stale, but the rule is still sensible.
* **Face table invariants:**
  * `glyphs[]` has exactly 95 entries in ASCII order.
  * `at` offsets are contiguous and sized exactly.
  * `advance >= 0`. `w = h = 0` is legal (space).
  * Consumers must map any byte outside 32..126 to space before indexing; all four blitters and all width helpers do.
* **Index coupling:**
  * Kernel `FACE_*` (`include/gfx.h:82-87`) must equal the `FACES_KERNEL` order. The comment warns: "the order changes whenever a size is added". `tools/harness.py:235-236` hard-codes the same order.
  * `UI_FACE_*` (`draw.h:138-143`) must equal the `FACES_USER` order.
  * `facetext` indices are only ever produced by `face_pick`, so they are order-independent.
* **Output format invariant:** every decoder produces `w*h*3` bytes, RGB, row-major, top-down, and `w, h >= 1` on success.

## 9. How to extend

* **Adding a face size:**
  1. Append a tuple to the relevant `FACES_*` list in `genface.py:953-983`. Append rather than insert: for the kernel and user lists, inserting shifts indices, and `include/gfx.h:79-81` warns about exactly that.
  2. Update `include/gfx.h` `FACE_*` or `userland/draw.h` `UI_FACE_*`, and the `order` list in `tools/harness.py:235-236`.
  3. Run `python tools/genface.py` from the repository root, then rebuild.
  4. Remember that every ring-3 program drawing text carries the whole of `userland/face.h`.
* **Adding glyphs beyond ASCII:**
  * genface: extend `ORDER` and the emitted `FACE_LAST`/`FACE_COUNT` (currently hard-coded to 32/126/95 at `:1054-1056`).
  * genfont: extend `FIRST`/`LAST` and `include/font.h`.
  * Every consumer maps out-of-range characters to space or skips them; they would need UTF-8 decoding and a character-to-index map.
  * The browser currently transliterates to ASCII (README `:1177-1182`).
* **Improving small sizes:** consider hinting or snapping stems to whole pixels in `rasterise`. Stems currently straddle columns, as §3.9 shows. `OVER` (overshoot) exists but is unused.
* **PNG:**
  * Adam7: seven passes, each with its own filtered rows and sub-image size, then a scatter step.
  * 16-bit: take the high byte.
  * tRNS colour key for types 0 and 2.
  * Fix the chunk bounds check (§10).
* **JPEG:**
  * Progressive: coefficient buffers per component, spectral selection and successive approximation, EOB runs.
  * Non-interleaved scans (`ns != ncomp`, and the single-component raster order).
  * Fill bytes before markers.
  * EXIF orientation.
  * Adobe APP14 RGB/CMYK.
  * A faster IDCT can be tested against the current one's output (`jpeg.h:177-179`).
* **SVG** (roughly in order of real-world impact):
  1. Paint inheritance from ancestors.
  2. `style` fill:none, opacity and stroke-width.
  3. Skip `<defs>`, `<clipPath>`, `<mask>`, `<symbol>`, `<pattern>` and `<marker>`.
  4. Close rect and polygon strokes.
  5. True elliptical arcs.
  6. `<use>`.
  7. Rounded `rect` (`rx`/`ry`).
  8. Stroke width under transforms.
  9. Treat `transparent` as no paint instead of white.
* **GIF:** `png.h:8` names GIF as one of the four web formats, but there is no decoder. It would need an LZW decoder plus sniffing (`GIF8`) in `browser.c:735-757`.
* **Inflate:** a table-driven decode would be much faster. Optionally verify Adler-32 and CRC-32. The existing contract must be kept: `inf_run` reports partial length on `INF_FULL`.
* **Pitfalls the comments warn about:**
  * Deflate bit order is LSB-first while Huffman codes are MSB-first (`inflate.h:22-25`).
  * Overlapping copies must go byte by byte (`inflate.h:142-145`).
  * PNG `bpp` is 1 for sub-byte depths (`png.h:65-69`), and rows must be unfiltered in order.
  * The JPEG cosine series needs the angle reduced first (`jpeg.h:194-203`).
  * JPEG edge blocks must still be decoded (`jpegtest.c:170-174`).
  * Cb and Cr are easy to swap (`jpegtest.c:86-90`).
  * Ramps legitimately step at block boundaries (`jpegtest.c:134-145`).
  * Never put an `svpath` on the stack (`svg.h:323-331`).
  * Read camelCase SVG attributes with `dom_attr_fold` (`svgtest.c:223-233`).
  * Union contours with max rather than even-odd (`genface.py:196-203`).
  * Monospace needs condensing, not just a replaced advance (`genface.py:995-1005`).
  * `piccheck` must read the program's own sentinel, not count PASS lines (`piccheck.py:28-33`).

## 10. Doc drift and suspicious code (verified)

### Likely bugs

1. **PNG chunk bounds check wraps: `png.h:146`.** `if (clen > (u32)(n - at - 12))`. When 8 ≤ `n - at` < 12 the right-hand side is a negative int cast to about 0xFFFFFFFC, so nearly any `clen` passes. The code then reads the chunk body past `data + n`: IHDR 13 bytes, PLTE up to 768, tRNS up to 256, and IDAT up to `n - zlen` bytes (`:178`). If `clen >= 0x80000000`, `at += 12 + (int)clen` (`:183`) makes `at` negative, and the next iteration reads before the buffer. Triggers are a PNG truncated within the first 12 bytes of its last chunk, or crafted input. The impact is an over-read or crash of the ring-3 browser. The existing truncation test (`pngtest.c:164-165`, n=20) does not reach this case.
2. **Truncation misreported as damage: `inflate.h:163-164`.** When the input ends while reading a length's extra bits or the distance code, `err` is already `INF_TRUNCATED`, but the combined test `if (s->err || dsym < 0 || dsym >= 30) s->err = INF_BAD` overwrites it. `png.h:204` then reports `PNG_BAD` instead of `PNG_TRUNCATED`. The effect is limited to the error code.
3. **`style="fill:none"` fills black: `svg.h:766-776`.** `sv_paint` correctly returns 0 for `none` found in `style`, but the default-black rule only checks for a `fill` *attribute* (`fv`). A stroke-only shape with its fill in `style`, which is typical of Inkscape and Illustrator output, therefore gets a solid black fill.
4. **Rect and polygon strokes miss their closing edge: `svg.h:614-625`, `661-671`, `448`.** `sv_shape` adds no closing point for `rect` or `polygon`. `sv_stroke` only strokes consecutive pairs (`for (i = from; i + 1 < to; i++)`). A stroked rect loses its left edge, and a polygon loses its last-to-first edge. Circles and ellipses are closed because their last cubic ends at the start point.
5. **No paint inheritance, and `<defs>`/`<clipPath>`/`<mask>` content drawn: `svg_render`, `svg.h:750-799`.** Only transforms are gathered from ancestors. `<g fill="#4285F4"><path/></g>` draws the path black. Shapes inside `<clipPath>`, `<mask>`, `<defs>`, `<symbol>` or `<pattern>` are painted as ordinary shapes, black by default. The header claims clipping and masks are "skipped" (`svg.h:32-33`), and the `sv_paint` comment says "not said … inherits" (`svg.h:485-486`).
6. **`fill="transparent"` paints white.** `sv_paint` passes the value to `css_color`, which maps `transparent` to `0xFFFFFF` (`css.h:231`). The result is a white shape drawn over whatever is below it.
7. **Single-component JPEG with sampling factors other than 1×1: `jpeg.h:288-337`, `409-418`.** MCUs of `h×v` blocks are decoded. Per ITU T.81 A.2.2 (quoted from memory), a one-component scan is non-interleaved, with one block per MCU in raster order, so such files decode scrambled. This is uncommon but does occur.
8. **JPEG fill bytes: `jpeg.h:366-377`.** `FF FF <marker>` makes `marker=0xFF` read as a segment with a length, which misparses the file. The spec allows any number of `FF` fill bytes before a marker.
9. **Minor undefined behaviour:**
   * `svg.h:554-560`: `translate()` or `scale()` with no numbers reads the uninitialised `a[0]`.
   * `jpeg.h:260`: a malformed DC size of up to 255 gives over-wide shifts in `jpg_bits` and `jpg_extend`.

### Doc drift

11. **`svg.h:36-38`** says a gradient fill "comes out as its first stop". The code (`:517-521`) uses flat grey `0x9A9A9A`, and the local comment at `:517-520` says grey.
12. **`svg.h:42-43` and `:54`** say edges are sampled "four times a pixel each way". In fact there are 4 vertical sub-scanlines and horizontal coverage is exact (`sv_span`). `genface.py:159-163` makes the same "sixteen samples" claim for the same scheme.
13. **`svg.h:435-438`** says a stroke is "a filled quadrilateral per segment plus a square at each joint". No joint squares are drawn.
14. **`svg.h:455-457`** says "One over the length, by Newton's method … Three rounds". The code computes the square root (Heron) with 12 rounds, then divides.
15. **`svg.h:326`** says "a program's stack is sixty four" KB. The stack now grows to 1 MB (`include/user.h:95-104`).
16. **`inflate.h:84-85`** says under-subscribed codes are "legal only for the one code case". The code never rejects incomplete codes.
17. **`png.h:112-114`** says the page background is the right `bg` "and the caller knows it". The only caller always passes white (`browser.c:737`, and `:755` for SVG).
18. **`png.h:222-223`** says "A picture that stopped part way is still a picture as far as it got". This only applies when inflate succeeded with short output. A truncated stream is `PNG_TRUNCATED` with no partial picture.
19. **`png.h:8`** lists GIF as a web picture format. No GIF decoder exists anywhere in the tree (grep).
20. **`jpeg.h:33-36`** says unsupported kinds are "Each … refused by name". Arithmetic and 12-bit files return the generic `JPG_UNSUPPORTED`. SOF3, SOF5-7 and SOF13-15 are not recognised and fail as `JPG_BAD` at SOS.
21. **`fetch.h:525-528`** (the consumer of `inflate.h`) says "identity, because there is no decompressor here … Close, because this makes one request per connection". The code sends `Accept-Encoding: gzip` and `Connection: keep-alive` (`:532-533`).
22. **`genface.py:44-45`** says "Bold is a fifth again". The weights are 126/92 and 107/78, both about +37%.
23. **`genface.py:55`**, `OVER = 12` "round shapes overshoot flat ones": the overshoot is never applied, and bowls sit exactly on 0, CAP and XH.
24. **`genface.py:169-170`**: the `_coverage` docstring says it takes "the larger value". It accumulates with `+=`; the max is taken in `rasterise`.
25. **`piccheck.py:10-13`** says "Those programs existed and nothing ran them". `ring3check.py:36-40` runs the same five programs, and it is always part of the gate (`gate.sh:302-303`).
26. **README.** `README.md:547` "Window chrome gets four [sizes]" is true of the regular sizes only; the kernel ships 8 faces and ring 3 ships 6. `README.md:1119` says page text is drawn "with the letterforms in `face.h`"; page text actually uses `facetext.h` (`tface_*`), and chrome uses `face.h`.
27. **Task-brief drift.** `inflate.h` contains no gzip wrapper; it is `wh_gunzip` in `fetch.h:151-182`. The JPEG IDCT is float, not fixed point, because ring 3 has SSE.
28. **Outside this area, noticed in passing.** `browser.c:708` says the reused picture buffer "is a megabyte"; `CSS_MAX` is 512 KB (`browser.c:59`). The `ring3check.py:1-4` docstring says "six things … All five" while listing 19 suites.

### Portability hazards in the generators

29. **`genfont.py:534,550`** writes in text mode with relative paths, so on Windows it produces CRLF files, which differ from the checked-in LF files. `genface.py:1160-1162` also needs to run from the repository root, but it writes LF. `genjpeg.py` only works on Windows (PowerShell with GDI+).

## 11. Open questions

1. How does `dom_parse` handle self-closing SVG elements (`<rect .../>`) and XML prologues or `<svg:svg>` namespaces? This decides whether sibling shapes nest wrongly, which only affects the transform chain because paint is not inherited anyway. That lives in `dom.h` and was not audited here.
2. Are the unused kernel faces (26 px, 15m, 15bm) and `face_surf_text` reserved for planned work, such as a terminal in the kernel or large titles, or are they leftovers that could be dropped from `FACES_KERNEL`?
3. Is GIF support intended? `png.h:8` implies it is expected.
4. Is running `pngtest`, `jpegtest`, `svgtest`, `layouttest` and `pagetest` in both `ring3check` and `piccheck` intentional? `piccheck` only runs in screen and full mode.
5. Would the generated face headers be byte-identical if regenerated on the maintainer's current host? The advance tables and a coverage spot check match. Full equality needs `python tools/genface.py` plus a diff, which could not be run here.
6. `genjpeg.py` output depends on the Windows GDI+ encoder version. Should the JPEG test data be frozen, as it is now in the tree, and treated as the reference, rather than regenerated?
7. What are the intended semantics of `png_decode`'s `bg` in the browser? Should it pass the element's computed background instead of white, as the `png.h:112-114` comment suggests?
