### 2.2 Main design decisions and their stated reasons

1. **TLS 1.3 only, one suite, one group.** TLS_AES_128_GCM_SHA256 (0x1301) over X25519.
   "A deliberate floor rather than a subset chosen for convenience ... the way that is
   prevented is by not implementing them, not by preferring against them. A server too old
   for 1.3 does not get a weaker connection here; it gets no connection" (`tls.h:17-23`,
   `tls.c:9-13`, README 1610-1617).
2. **The transcript is "the spine".** "the order of hashing against verifying is exactly as
   important as the arithmetic" (`tls.c:15-19`); CertificateVerify and Finished hashes are
   taken before the message is added (`tls.c:726-737`).
3. **One session per TCP connection, named by the TCP handle** (the latest commit, "A TLS
   session per connection, rather than one for the machine"). Reason: "a page and its
   pictures were fetched one encrypted connection after another ... because there was nowhere
   to put a second" (`tls.h:4-15`, `tls.c:92-111`). NOTE: the syscall layer still allows only
   one secure socket machine-wide -- see §10.2.
4. **Errors are sentences for people.** `tls_error` "is meant to be shown to somebody"
   (`tls.h:25-28`). The last failure is also copied to a machine-wide slot `nowhere`, because a
   failed handshake has usually closed its connection by the time somebody asks why
   (`tls.c:113-123`, `tls.h:42-46`).
5. **No key without entropy**: `rng_ready()` false → refuse (`tls.c:598-604`; `rng.h:17-19`).
6. **Parser for hostile input**: every DER length is "a claim and not a fact"
   (`x509.c:3-7`, `x509.h:8-13`). Answers come from a small closed set of reasons, "There is
   no 'mostly valid'" (`x509.c:9-11`).
7. **Names compared as raw bytes** -- "stricter than the standard allows and has never let the
   wrong certificate through" (`x509.h:40-44`).
8. **Times packed as `yyyymmddhhmmss` integers** so comparison needs no calendar arithmetic
   (`x509.h:48-49`, `x509.c:130-131`).
9. **Hostname: SAN dNSName only; CN is ignored**; wildcard covers exactly one leftmost label
   (`x509.c:489-494`, `516-519`).
10. **Chain building by name, not position**, because servers send duplicates, extras, the
    root, out of order (www.geeksforgeeks.org sends the leaf twice) (`x509.c:575-594`);
    **stop at the first certificate that is itself a trust anchor** (archive.org's Go Daddy
    root arrives cross-signed by the removed SHA-1 Go Daddy Class 2 root) (`x509.c:602-616`);
    **stop at a self-signed certificate** (archive.org also sends a nameless fourth cert)
    (`x509.c:620-632`); **a served root is replaced by the store's copy** and its
    self-signature is never checked ("Verifying a self-signature proves nothing anyway")
    (`x509.c:665-679`).
11. **Public-key verification is not constant time on purpose**: "every number involved is
    public" (`rsa.h:7-10`, `rsa.c:15-16`, `ec.h:11-13`, `ec.c:391-392`). **X25519 is constant
    time** (secret scalar; mask-based cswap) (`x25519.c:9-12`). **GHASH is bit-serial rather
    than table-driven** because tables make timing data-dependent (`gcm.c:9-13`). AES itself
    uses S-box tables (see §10.12).
12. **Montgomery arithmetic with constants built by repeated doubling**, "which avoids
    writing long division altogether" (`rsa.c:11-13`, `rsa.c:140-147`, `ec.c:172-173`).
    `ec.c` deliberately does NOT use the special-form fast reductions of the NIST primes,
    because that is "where implementations of these curves most often go wrong" (`ec.c:16-22`).
13. **Known answers from published documents, not self-agreement** (`crypto.h:17-21`,
    `sha256.h:10-12`, README 1362-1369).
14. **Root store is generated from a published store**, not chosen here (`roots.h:5-18`,
    `roots.c:1-15`, `mkroots.py:10-16`).
15. **WPA2 arithmetic is written and tested before any radio exists** -- "the key arithmetic,
    not the conversation" (`wpa.c:1-3`, README 1240-1260). `kernel/wifi.c` only detects
    hardware; nothing calls `wpa_*` outside selftest.

#### Global state

- `static tls_t sessions[TCP_MAX]` (105). `TCP_MAX` = 6 (`include/tcp.h:17`). **This is the
  session table: 6 entries, index == TCP handle.**
- `static tls_t nowhere` (106): where any out-of-range handle lands (`tls_of`, 108-111), and
  the machine-wide copy of the last error (`fail`, 122) and the last description (826).
- Function-scope statics inside `tls_connect`, **shared by all sessions**:
  `static x509_t leaf` (669), `static const u8 *ders[X509_MAX_CHAIN]` (673),
  `static u32 lens[X509_MAX_CHAIN]` (674), `static u8 *chain_store` (676, `kmalloc(HS_MAX)`
  once, never freed). Plus `x509_verify_chain`'s `static x509_t chain[X509_MAX_CHAIN]`
  (`x509.c:564`). See §6 and §10.3.

#### How a session is bound to a TCP connection

`tls_of(tcp)` (108-111) is the whole binding: `tcp < 0 || tcp >= TCP_MAX` → `&nowhere`,
otherwise `&sessions[tcp]`. There is no generation counter, no ownership check and no check
that the TCP handle is open; `tls_connect` stores `z->tcp = tcp` (589) and uses it for every
`tcp_send`/`tcp_recv`. The pairing discipline (call `tls_close` before `tcp_close`, never reuse
a handle without `tls_connect`) is kept by the two callers: `kernel/syscall.c:725-730`
(`sock_drop`) and `kernel/http.c:52-55` (`done`). Ownership per process is enforced one layer
up by `sock_of` (`syscall.c:735-740`).

## 4. Control flow and lifecycles

### 4.1 Session lifecycle (per `sessions[h]` slot)

```
 FRESH (zeroed BSS, no buffers)
   │ tls_connect(h, host)   memset except buffer pointers; buffers allocated on first use
   v
 HANDSHAKING (open = false)
   ├── failure ──> FAILED (open = false, error set, copied to nowhere.error); caller closes TCP
   └── success ──> OPEN (open = true, described set, error cleared, bb_log "tls ... to host")
                    │ peer warning-level alert, or read failure inside tls_recv
                    v
                  ENDED (open = true, ended = true; tls_ended true once app buffer drained)
                    │ tls_close(h)  (close_notify sent only if open)
                    v
                  CLOSED (open = false; buffers kept; keys/secrets still in memory)
                    │ next tls_connect on the same handle
                    └──> HANDSHAKING
```

### 4.2 `tls_connect` step by step (`tls.c:581-829`)

1. Slot = `tls_of(tcp)`. Save `rec/hs/app`, `memset` the struct, restore, `z->tcp = tcp`
   (586-589). `tls_connect(-1, …)` works on `nowhere` and allocates ~66 KB of buffers for it.
2. `alloc_buffers` or fail "not enough memory for a connection" (591).
3. Copy host (≤ 255 chars); empty → "no host name to check a certificate against" (593-596).
4. `rng_ready()` or "this machine has no source of randomness, so no key can be made" (601-604).
5. `priv`, `client_random`, `session_id` ← `rng_bytes`; `pub = x25519_public(priv)` (606-609).
6. `sha256_init(&transcript)` (611).
7. **ClientHello** built at `z->rec + 4` (`build_client_hello`, 351-424), 4-byte handshake
   header added (617-620), whole message hashed (622), copied to a temporary `kmalloc` buffer
   (the record buffer is reused for reading) and sent as one plaintext handshake record
   (624-632).

   | Field | Bytes | Value |

   | random | 32 | `client_random` |
   | legacy_session_id | 1 + 32 | `20` + random `session_id` (360-361) |
   | cipher_suites | 2 + 2 | `00 02`, `13 01` (363-364) |
   | legacy_compression_methods | 1 + 1 | `01 00` (366) |
   | extensions length | 2 | patched at 422 |
   | server_name 0x0000 | 4 + 2 + 1 + 2 + host | list len host+3, type 0 host_name (373-382); sent even for IP literals |
   | supported_versions 0x002b | 4 + 1 + 2 | `02`, `03 04` (385-388) |
   | supported_groups 0x000a | 4 + 2 + 2 | `00 02`, `00 1d` (391-394) |
   | signature_algorithms 0x000d | 4 + 2 + 8 | `04 03` ecdsa_secp256r1_sha256, `08 04` rsa_pss_rsae_sha256, `05 03` ecdsa_secp384r1_sha384, `04 01` rsa_pkcs1_sha256 ("for the certificates") (399-411) |
   | key_share 0x0033 | 4 + 2 + 2 + 2 + 32 | client_shares len 36, group `00 1d`, len 32, `pub` (415-420) |

   Body = 155 + host_len bytes. Not sent: ALPN, psk_key_exchange_modes, pre_shared_key,
   early_data, signature_algorithms_cert, status_request, padding, cookie. No dummy
   ChangeCipherSpec is ever sent by the client.
8. **ServerHello** (635-641): `hs_next` in plaintext mode; must be type 2;
   `parse_server_hello` (428-499):
   - `len ≥ 38`; legacy_version not checked;
   - random equal to the HelloRetryRequest magic `RETRY[32]` (431-435) → fail "the server
     wants a key exchange group this does not have" -- **HRR is never handled, always refused**
     (also when the HRR is only for a cookie);
   - legacy_session_id_echo: bounds checked, **content not compared** with what was sent;
   - cipher_suite must be 0x1301 (450-454); compression byte skipped, not checked;
   - extensions: `0x002b` must have length 2 and value 0x0304 (469-476); `0x0033` must be
     group x25519, 32-byte key, `n == klen + 4` (477-487); all others ignored; duplicates not
     detected; both are required (491-497).
   Then the whole ServerHello is added to the transcript (640).
   **Not checked**: that the ServerHello ended at a record boundary (RFC 8446 §5.1 requires
   messages preceding a key change to align with a record boundary) -- leftover plaintext
   handshake bytes in `z->hs` would be consumed as if they were encrypted-phase messages.
9. `shared = x25519(priv, peer_share)`; all-zero → "the server's key share is not usable"
   (644-648).
10. **Handshake keys** (650-666) -- see §4.4. Only the *read* direction is keyed now
    (`set_keys(z, s_hs, false)`, 665).
11. **Encrypted flight loop** (681-756), each message via `hs_next(z, true, …)`:
    - `EncryptedExtensions` (8): added to the transcript; contents not parsed (685-686).
    - `Certificate` (11): certificate_request_context (length byte, content skipped, not
      required to be empty); 24-bit list length; entries while `nchain < X509_MAX_CHAIN`:
      each DER copied into `chain_store` (bounded by `HS_MAX`), `ders[]/lens[]` filled,
      per-certificate extensions skipped; entries beyond 8 silently ignored; no entries →
      "the server sent no certificate"; leaf = `x509_parse(ders[0])` or "the server's
      certificate could not be read"; `have_leaf = true`; added to the transcript (688-722).
    - `CertificateVerify` (15): requires `have_leaf`; `hash_before_verify =
      transcript_hash` (before adding); `check_cert_verify`; then added (724-730).
    - `Finished` (20): `upto_here = transcript_hash`; `fkey = Expand-Label(s_hs, "finished",
      "", 32)`; `want = HMAC-SHA256(fkey, upto_here)`; `len == 32 && memcmp(want, body, 32) ==
      0` (non-constant-time `memcmp`) or "the server's finished message is wrong"; added;
      **break** (732-750).
    - Anything else (e.g. CertificateRequest 13) → "the server sent an unexpected handshake
      message" (752-755).
    - **Ordering is not enforced and CertificateVerify is not required**: the loop exits on
      Finished regardless of whether a CertificateVerify was seen (§10.1).
12. `have_leaf` or "the server never sent a certificate" (758).
13. `x509_verify_chain(ders, lens, nchain, host, x509_now())`; non-OK → `fail(x509_reason(r))`
    (761-765).
14. **Client Finished and application keys** (768-820): `th = transcript_hash` (through the
    server Finished); `set_keys(z, c_hs, true)`; `mac = HMAC(Expand-Label(c_hs, "finished",
    "", 32), th)`; send encrypted handshake message `14 00 00 20 ‖ mac` (c_seq 0); master
    secret; `c_app`/`s_app` over the same `th`; both directions re-keyed; `keys_are_app =
    true`. The client Finished is never added to the transcript (nothing needs it without
    resumption).
15. `open = true`, `handshake_done = true`, `error[0] = 0`, `described = "TLS 1.3, x25519,
    aes-128-gcm"` (fixed string, `kformat`), copied to `nowhere.described`,
    `bb_log("tls %s to %s")` (822-828).

On any failure the function returns false without sending an alert and without touching the
TCP connection; callers close TCP (`syscall.c:802`, `http.c:89-93`).

**`check_cert_verify`** (503-570): message = `u16 scheme ‖ u16 sig_len ‖ sig`, exact length.
Content signed = 64 × 0x20 ‖ `"TLS 1.3, server CertificateVerify"` ‖ 0x00 ‖ transcript hash
(SHA-256, 32 bytes). Both SHA-256 and SHA-384 of the content are computed. Schemes:
`0x0403` → leaf must be EC P-256, DER signature split, `ec_verify(P-256, …, h256)`;
`0x0503` → leaf must be EC P-384, `ec_verify(P-384, …, h384)`; `0x0804` → leaf must be RSA,
`rsa_verify_pss(…, h256)`; anything else (including 0x0401, which TLS 1.3 forbids here) →
"the server signed with something this cannot check". Key/scheme mismatch or a bad signature →
"the server's signature over the handshake is wrong".

### 4.3 Record layer and data path

**Write**: `tls_send` → ≤8192-byte chunks → `send_encrypted` (inner type 23) → `write_all`
(header 5 bytes, then body+tag, each in ≤1400-byte TCP segments, each waiting for its ACK).
Nonces: `c_iv XOR c_seq`; `c_seq` reset to 0 by every `set_keys(…, true)`. No padding, no
record size limit negotiation, no KeyUpdate ever sent, no sequence-number wrap check.

**Read** -- `read_record(z, &type, &len, encrypted)` (217-269):
1. 5-byte header via `read_exact(…, 20000)` or "the connection stopped".
2. `n == 0 || n > REC_MAX` → "the server sent a record of an impossible size".
3. Body via `read_exact(…, 20000)` into `z->rec` or "the connection stopped mid record".
4. Outer type 20 (CCS) → returned as `REC_CHANGE_CIPHER`, len 0 -- accepted at any time, also
   after the handshake; body not checked to be `01`.
5. Outer type 21 while not encrypted → "the server refused the connection".
6. Not encrypted → return outer type and length.
7. Encrypted: `n ≥ 17`; `gcm_open(s_gcm, nonce_for(s_iv, s_seq), AAD = header, …)` or "a
   record did not authenticate" (outer type is not required to be 23); `s_seq++`; strip
   trailing zero bytes; empty → "a record had nothing in it"; inner type = last byte.
8. Inner alert: `len ≥ 2 && rec[0] == 1` (level warning -- any description, not only
   close_notify) → `ended = true`, len 0, true. Otherwise "the server closed the connection
   with an alert".

**`tls_recv`** (846-889):
1. `!open` → 0.
2. Bytes left in `z->app` → copy `min(have, cap)`, return.
3. `ended` → 0.
4. `deadline = now + timeout_ms`; loop: past deadline → 0; `read_record(encrypted)` -- this
   can itself block ~20 s per header or body; on failure `ended = true`, return 0 (the reason
   is in `z->error`); if `ended` (close alert) → 0; CCS → continue; **any handshake record
   (NewSessionTicket, KeyUpdate, CertificateRequest) is dropped** (872-876); other non-appdata
   types → continue; empty → continue; copy the record into `z->app` and return the first
   `min(len, cap)` bytes.
5. Timeout semantics: `timeout_ms` is only checked between records, so with a silent peer the
   call blocks ≈20 s (the `read_exact` deadline) regardless of `timeout_ms`, and then marks the
   session ended ("the connection stopped"). A TCP FIN without close_notify is reported the
   same way as a clean close (truncation not distinguishable, as `syscall.c:862-865` says).
6. 0.5-RTT data: server application data sent right after its Finished is decrypted correctly,
   because `s_app` is installed before `tls_connect` returns.

**`tls_close`**: close_notify `{1, 0}` if open; state cleared (891-904).

### 4.5 Certificate chain verification (`x509_verify_chain`, `x509.c:560-704`)

1. `n == 0 || n > 8` → `X509_BAD_PARSE` (562).
2. Parse **all** `n` certificates into `static chain[]`; any failure → `X509_BAD_PARSE`
   (564-566) -- including unrelated extra certificates the server left in (§10.5).
3. `chain[0]` must match `host` by SAN → else `X509_WRONG_NAME` (570).
4. Leaf dates (skipped when `now == 0`) → `X509_NOT_YET_VALID` / `X509_EXPIRED` (572-573).
5. Walk (595-657): `top = leaf`, `used = {0}` (bitmask), `below = NULL`, `depth = 0`. Loop:
   a. `roots_find(top->subject)` → stop: top is an anchor (617-618);
   b. subject == issuer (bytes) → stop: self-signed (630-632);
   c. first unused `k` with `chain[k].subject == top->issuer` (bytes); none → stop (634-643);
   d. parent checks, in order: basicConstraints present and CA → else `X509_NOT_A_CA`;
      `path_len ≥ 0 && depth > path_len` → `X509_NOT_A_CA`; parent dates →
      `NOT_YET_VALID`/`EXPIRED`; `x509_signed_by(top, parent)` → else `X509_BAD_SIGNATURE`
      (645-651);
   e. mark used, `below = top`, `top = parent`, `depth++` (653-656).
6. If `top->subject` is in the store (680-695): `below == NULL` (the leaf itself is an
   anchor) → `X509_UNTRUSTED`; parse the **store's** copy → `anchor`; must be CA; verify
   `below` against the store copy → `X509_OK` / `X509_BAD_SIGNATURE`. The served root is set
   aside; its self-signature is never checked (so SHA-1-self-signed roots are fine).
7. Else (697-703): `roots_find(top->issuer)` or `X509_UNTRUSTED`; parse store copy; must be
   CA; `x509_signed_by(top, anchor)` → `X509_OK` / `X509_BAD_SIGNATURE`.

**Rules summary**: path length via `pathLenConstraint` (counted from the leaf's issuer =
depth 0; anchor's own constraint not checked); validity of leaf and every served parent
(**store anchors' dates are never checked**); "now" = RTC via `x509_now()`, fail-open when 0;
hostname = SAN dNSName with one-label wildcard; SHA-1 refused implicitly (unknown OID →
`X509_BAD_SIGNATURE` "a signature in the chain is wrong", not `X509_UNSUPPORTED`); self-signed
roots trusted only by store identity. **Not implemented**: keyUsage, extendedKeyUsage
(serverAuth), nameConstraints, unknown-critical-extension rejection, policies, revocation
(no OCSP/CRL/stapling), CT, AKI/SKI matching, backtracking among same-subject candidates.

### 4.6 Signature verification flows

**ECDSA** (`ec_verify`, `ec.c:464-541`): `curve_setup`; key length `1 + 2·bytes` and prefix
0x04 (uncompressed only); `1 ≤ r_len, s_len ≤ bytes`, `1 ≤ hash_len ≤ 64`; r, s left-padded;
r, s ∈ [1, n−1]; Qx, Qy < p; Q on curve; e = leftmost `bytes` bytes of the hash (left-padded
if shorter), reduced once mod n; w = s⁻¹ mod n (Fermat, in the order field); u1 = e·w, u2 = r·w;
R = u1·G + u2·Q (two separate `pt_mul`, then `pt_add`); infinity → false; x(R) mod n == r.
Any failure is a plain `false` by design (`ec.h:26-29`).

**RSA PKCS#1 v1.5**: `rsa_public` (length/parity/range checks) → modexp → full-block
structural comparison (`rsa.c:221-253`). **RSA-PSS**: modexp → 0xBC trailer, top bit, MGF1
unmask, zeros‖01‖salt, H' comparison (`rsa.c:278-328`).

## 6. Concurrency, locking, memory ownership, invariants

- **Locking model around it**: one big kernel lock; the syscall gate is an interrupt gate
  (`set_gate(0x80, …, 0xEE)`, `idt.c:63`), so syscalls start with interrupts off and nothing
  in the TLS/TCP wait paths re-enables them; kernel tasks (e.g. the shell running
  `http_get`) run with interrupts on and can be preempted by the timer (`idt.c:254-270`). TLS
  has no locks of its own.
- **Per-slot state** is independent across slots, but **shared state remains**:
  `tls_connect`'s statics `leaf`, `ders`, `lens`, `chain_store` (`tls.c:669-679`) and
  `x509_verify_chain`'s `static x509_t chain[8]` (`x509.c:564`). Two handshakes interleaving
  would corrupt each other. Today this is mostly masked because `sys_connect_tls` refuses a
  second *established* secure socket (`syscall.c:786-787`) and syscalls are not preempted
  mid-busy-wait; the kernel shell's `fetch https://…` (a preemptible kernel task) has no such
  guard (§10.3).
- `nowhere.error` / `nowhere.described` are last-writer-wins across all sessions; with several
  users `SYS_TLS_STATUS` can report another connection's failure.
- `crypto.c` `build_inverse` (197-204) lazily fills `INV_SBOX` -- idempotent, benign.
- **Memory ownership**: session buffers are owned by the slot for the machine's lifetime
  (never freed); `chain_store` is allocated once; the ClientHello copy is `kmalloc`/`kfree`d
  per handshake (626-630). Worst case heap: 7 slots (6 + `nowhere`, which selftest touches via
  `tls_connect(-1, "")`) × 66,112 B + 32 KB ≈ 495 KB. `x509_t` fields alias DER buffers
  (`chain_store`, `testcerts.h`, `roots.c`). `hs_next` pointers alias `z->hs` until the next
  call.
- **Invariants**: sequence numbers reset whenever a direction is re-keyed (`set_keys`); a
  (key, nonce) pair is never reused because each direction has its own key and counter;
  transcript updated strictly in message order; CertificateVerify and Finished verification use
  the hash taken *before* adding the message; the client Finished is never in the transcript;
  `z->rec` is shared by sending and receiving, which is safe only because `tls_recv` copies a
  record into `z->app` before returning and the handshake never sends while holding
  `z->rec`-based pointers.
- **Secret hygiene**: `priv`, all traffic secrets and GCM round keys remain in the slot after
  `tls_close` until the next `tls_connect` on that handle; stack copies (`shared`, finished
  keys, clamped scalars) are not wiped. Failed `gcm_open` wipes the buffer.
- **Stack depth**: certificate verification is the deepest kernel path (README 1381-1389:
  "a little over sixteen kilobytes" with interrupts; `TASK_STACK_SIZE` is now 32768,
  `include/sched.h:32`). Big frames: `rsa_verify_pkcs1` (`em[512]`) → `rsa_public` (3 `bn_t`)
  → `bn_mod_exp` (5 `bn_t` + `mont_mul`'s `t[66]`), `rsa_verify_pss` (`em[512]`, `db[512]`),
  `ec_verify` (`curve_t` + ~20 `fe` + 5 points), `x509_verify_chain`'s local `x509_t anchor`.
  `test_stack` (`selftest.c:1718-1731`) requires ≥ 1/4 of the stack unused at the end of the
  run.

## 9. How to extend (where, how, and the pitfalls the comments warn about)

1. **Require CertificateVerify and enforce message order (do this first).** In the loop at
   `tls.c:681-756` track `have_cv` (set only after `check_cert_verify` succeeds) and at
   `HS_FINISHED` require `have_leaf && have_cv`; better, enforce EE → Certificate →
   CertificateVerify → Finished exactly once each. Add a selftest that feeds a synthetic flight
   without CertificateVerify (needs a way to drive `hs_next` from a buffer).
2. **Allow several concurrent TLS connections from userland** (what the latest commit is
   for): (a) move `leaf`, `ders`, `lens` and `chain_store` into `tls_t` or a per-handshake heap
   block, and make `x509_verify_chain`'s `chain[]` caller-provided or heap-allocated;
   (b) delete the busy check at `syscall.c:786-787` and fix `sock_take` (`syscall.c:742-745`),
   which does not reserve the slot before the blocking `tcp_open`/`tls_connect`; (c) make
   `SYS_TLS_STATUS` per socket (a handshake that failed has no socket; keep `-1` for that);
   (d) update README 1606-1609, `syscall.c:775-778`, `sdk/zelr.h:439-442`,
   `include/syscall.h:83, 198`, `userland/fetch.h:29`, `userland/browser.c:481-482`.
3. **KeyUpdate**: in `tls_recv` (`tls.c:872-876`) parse handshake messages instead of
   dropping records; on type 24 derive `s_app' = Expand-Label(s_app, "traffic upd", "", 32)`,
   `set_keys(…, false)`, and if `request_update == 1` send a KeyUpdate and roll `c_app`.
   NewSessionTicket can keep being ignored.
4. **HelloRetryRequest / P-256 ECDHE**: RFC 8446 makes secp256r1 the MUST-implement group.
   `ec.c` is verification-only and deliberately variable-time; ECDHE needs a constant-time
   scalar multiplication (a Montgomery ladder with masked selects) and point validation. HRR
   handling means: detect `RETRY`, replace the transcript with `message_hash` (type 254 +
   Hash(CH1)), send a second ClientHello with the requested group/cookie.
5. **TLS_AES_256_GCM_SHA384 / ChaCha20-Poly1305**: `sha256.c`'s HMAC/HKDF/Expand-Label and
   `tls_t.transcript` are SHA-256-only; generalize to a hash descriptor first. AES-256 already
   exists; ChaCha20/Poly1305 do not.
6. **Resumption**: needs the transcript through the client Finished (currently never added),
   `res master`, NewSessionTicket parsing, PSK + binder in the ClientHello.
7. **X.509 hardening**: prefer store anchors before walking to a served parent (check
   `roots_find(top->issuer)` and verify directly -- fixes §10.4); parse served certificates
   lazily so an unusable extra certificate does not fail the chain (§10.5); enforce EKU
   serverAuth, keyUsage keyCertSign on CAs / digitalSignature on the leaf, reject unknown
   critical extensions, add iPAddress SANs, nameConstraints; return `X509_UNSUPPORTED` for
   SHA-1 and unknown algorithms instead of `X509_BAD_SIGNATURE`.
8. **Roots**: regenerate with `python tools/mkroots.py [bundle.pem]` (defaults to
   `certifi`), then `python tools/mkroots.py --check`. Selftest depends on the store containing
   GTS Root R1 (chain checks, `selftest.c:2250, 2287`) and GlobalSign Root CA - R3 (SHA-384
   check, 2315) and on `roots_count() > 10`. `mkroots.py` keeps only the first certificate per
   subject -- a re-keyed root with the same DN would be dropped (and `roots_find` could only ever
   return the first anyway).
9. **Replacing `testcerts.h`**: the leaf expires 2026-11-27; the chain checks use fixed times
   (`when = 20261001000000`, `selftest.c:2248`) and must stay inside the new leaf's validity;
   byte offsets in the tamper tests (`tampered[110]` at 2272, `bent[200]` at 2327) must be
   re-derived (see §10.10).
10. **Performance**: coalesce the 5-byte record header with the body into one buffer
    (`z->rec` has 64 bytes of slack, `tls.c:575`) -- today every record costs at least two
    ACK-waited TCP segments (`tls.c:186-187, 210-211`).
11. **WPA**: before a driver uses it, raise `mic_of`'s 256-byte copy limit (or HMAC in pieces
    with the MIC field substituted), and add AES-CMAC (key descriptor v3) if WPA2-PSK-SHA256 or
    PMF is needed. IEEE 802.11 also publishes PRF test vectors that could replace the
    self-composed PRF checks (from general knowledge of the standard; not verified here).

Pitfalls the comments warn about (keep these in mind when touching the code):
- `fe_add_mod`/`fe_sub_mod` must work in a local copy because `out` may alias the second
  operand (`ec.c:153-157`).
- SPKI is two levels deep; reading the first child as the algorithm fails on every certificate
  (`x509.c:185-189`). INTEGER leading zeros are sign, not value (`x509.c:213-214`).
- The TBS bounds must be taken before entering it (`x509.c:323-325`).
- Hash the transcript before adding CertificateVerify/Finished; application secrets are over
  CH…server Finished (`tls.c:726-736, 769-771, 798-810`).
- PKCS#1 padding must be checked along its whole length; PSS DB must be checked for both the
  zeros and the 0x01 (`rsa.c:235-237, 306-308`).
- HKDF-Extract with no salt uses a block of zeros; the TLS "no PSK" IKM is 32 zero bytes, not
  empty (`selftest.c:1525-1527, 1544-1546`).
- Two moduli per curve (p and n): reduce x(R) mod n, not mod p (`ec.c:8-14, 537-539`).
- WPA: Min/Max ordering of addresses and nonces; the PRF's zero byte and trailing counter
  (`wpa.h:27-31`, `wpa.c:14-20`); checking a MIC must not modify the frame (`wpa.c:68-72`).
- Stack depth of certificate verification (README 1381-1389).

## 10. Doc drift and suspicious code (verified; ordered by severity)

### 10.1 CRITICAL -- CertificateVerify is optional: server authentication can be bypassed
`tls.c:681-756`: the encrypted-flight loop accepts EncryptedExtensions, Certificate,
CertificateVerify and Finished in any order and breaks out on Finished; after the loop only
`have_leaf` is checked (758). There is no flag recording that a CertificateVerify was received
and verified. A man in the middle can therefore answer the ClientHello with its own X25519
share (so it knows the handshake keys), send the real site's public certificate chain (which
passes `x509_verify_chain` for the requested host), **omit CertificateVerify**, and send a
valid Finished computed from `s_hs`. The client verifies Finished (the attacker can compute
it), verifies the chain, sends its Finished and derives application keys the attacker also
has. Result: full interception of any https connection, including from the browser. This
contradicts `tls.c:1-7` ("A connection with the first two and not the third is encrypted to a
stranger") and README 1192-1195. No selftest or `tlscheck.py` case covers it (real servers
always send CertificateVerify).

### 10.2 Drift -- "one session at a time" is still enforced one layer up
- `tls.c`/`tls.h` now hold `sessions[TCP_MAX]` (6), one per TCP handle.
- `kernel/syscall.c:775-778` still says "the TLS session state in kernel/tls.c is still
  single ... a second handshake would quietly take the first one's keys", and
  `sys_connect_tls` still returns `NET_ERR_BUSY` if any open socket is secure (786-787). So a
  userland program still gets **one** encrypted socket machine-wide; the stated goal of the
  commit (page + pictures concurrently) is not reachable from userland. Kernel-internal
  `http_get` is not restricted.
- README 1606-1609 ("TLS is one session at a time ... A second handshake is refused") describes
  the syscall behaviour correctly but gives a reason that is no longer true; `sdk/zelr.h:439-442`
  and `include/syscall.h:83` ("The same one socket"), `include/syscall.h:198` and
  `userland/fetch.h:29` (`NET_ERR_BUSY`/`WEB_ERR_BUSY` "the one connection is already in use"),
  and `userland/browser.c:481-482` are stale in the same way.
- The busy check looks only at *established* secure sockets (`secure` is set at
  `syscall.c:807` after the handshake), so it does not stop two handshakes that overlap.

### 10.3 Latent race -- shared statics inside the per-session design
`tls.c:669-679` (`static x509_t leaf`, `ders[]`, `lens[]`, `chain_store`) and `x509.c:564`
(`static x509_t chain[8]`) are shared by all sessions. If a preemptible kernel task (the shell's
`fetch https://…` → `http_get` → `tls_connect`) is preempted mid-handshake and a user process
runs a complete `sys_connect_tls`, the shell's handshake resumes with another host's
certificates in `chain_store`/`ders` and another leaf in `leaf`. It becomes a real bug as soon
as §10.2's restriction is lifted. (Whether two *syscalls* can interleave depends on the
interrupt/lock model -- see §11.)

### 10.4 Likely bug -- an expired served copy of a trusted root fails the chain
In the walk (`x509.c:601-657`) the served parent's CA flag, path length, **dates** and
signature are checked (646-651) *before* the next iteration notices that the parent is a store
anchor (617). A server that still sends an expired cross-signed copy of a root the store
trusts is rejected with `X509_EXPIRED` although the store's own copy is valid. Example: the
old Let's Encrypt long chain `leaf → R1x → ISRG Root X1 (cross-signed by DST Root CA X3,
expired 2024-09-30)` fails, while `leaf → R1x` alone would pass (ISRG Root X1 is in the store,
`roots.c:4073`). This is the AddTrust-2020 failure mode.

### 10.5 Fragility -- any unparseable certificate in the served list fails the whole chain
`x509.c:565-566` parses all `n` certificates up front. An extra, unneeded certificate with a
key this code does not read (Ed25519, P-521, DSA, RSA < 1024 bits, RSA-PSS SPKI) or with odd
DER makes the connection fail with "the certificate could not be read", although the comment
at 578-581 acknowledges servers leave unrelated certificates in.

### 10.6 `tls_recv` timeout semantics
`timeout_ms` is only checked between records (`tls.c:861-862`); `read_record` blocks up to
20 s per header/body (`tls.c:219, 223`). So `sys_recv`'s 4000 ms (`syscall.c:860`) becomes
≈20 s, and a peer silent for 20 s marks the session `ended` with "the connection stopped"
(`tls.c:865-867`) -- a slow server looks like a finished answer (`sys_recv` then returns −2).

### 10.7 KeyUpdate unsupported; handshake records after the handshake are dropped
`HS_KEY_UPDATE` (48) and `HS_NEW_TICKET` (43) are never used; `tls_recv` drops every
post-handshake handshake record (872-876). A server KeyUpdate makes every later record fail
with "a record did not authenticate".

### 10.8 Protocol-conformance gaps (not exploitable by themselves given 10.1)
- No record-boundary check at the key change after ServerHello (`tls.c:635-641`; RFC 8446
  §5.1).
- legacy_session_id_echo not compared (`tls.c:446-448`); compression byte and legacy_version
  not checked.
- CCS accepted at any time, including after the handshake (`tls.c:225-231, 870`).
- Any *warning*-level encrypted alert is treated as close_notify; the description byte is
  never read (`tls.c:264`), although the comment says "the second byte says" (263).
- No alert is sent to the server on any failure.
- HRR refused even when it is only asking for a cookie.
- SNI sent for IP literals (`tls.c:373-382`); IP SANs unsupported (`x509.c:529`), so
  `connect_tls("1.2.3.4")` can never succeed.

### 10.9 X.509 policy gaps
Critical flag ignored -- unknown critical extensions accepted (`x509.c:266-276`); keyUsage,
extendedKeyUsage and nameConstraints not parsed (OIDs absent, 95-106); store anchors' dates
and pathLen never checked (680-703); `dates_ok` accepts everything when `x509_now()` returns 0
(`x509.c:554`); `X509_UNSUPPORTED` is dead -- SHA-1-signed certificates report
`X509_BAD_SIGNATURE` "a signature in the chain is wrong" (`x509.c:115, 403-417, 651`), the
misleading message `tlscheck.py:50-53` itself complains about; PSS parameters in certificates
ignored (SHA-256/salt 32 assumed); no backtracking between same-subject candidates
(`x509.c:634-642`).

### 10.10 Test drift
- `selftest.c:2270-2272`: the comment says the altered byte is "Inside the validity dates" and
  must be "caught by arithmetic". In the current `test_cert0`, byte 110 is `0x0d`, the
  **length byte of the notBefore UTCTime** (bytes 108-110 = `1e 17 0d` at
  `testcerts.h:27`). It becomes `'5'` (0x35 = 53), overrunning the 30-byte Validity, so the
  chain is refused by the DER parser (`X509_BAD_PARSE`), not by signature arithmetic. The check
  still passes, for a different reason (probably an artifact of re-capturing the certificate).
  The SHA-384 tamper (`bent[200]`) does hit a signed byte (an inner SEQUENCE tag in the subject)
  and genuinely tests the signature.
- `selftest.c:2231-2232`: labelled "and it is not the bare domain" but tests
  `nonesuch.example.org`; `google.com` against `*.google.com` is never tested.
- README counts: `[certificates]` 39 vs 40 executed; `[tls 1.3]` 19 vs 26 (the new `test_tls`
  adds one check plus one per slot, `selftest.c:1765-1768`); so the README total of 552
  (README 1330, 1359) is at least 8 low.

### 10.11 README inaccuracy about X25519
README 1610-1611: "AES-128-GCM with SHA-256 over X25519, which every 1.3 server must
implement". RFC 8446 §9.1 makes secp256r1 the MUST and X25519 a SHOULD (from knowledge of the
RFC). A P-256-only server answers with HelloRetryRequest, which is refused
(`tls.c:440-443`). `tls.h:17-19` is phrased more carefully (the suite is the MUST).

### 10.12 Comment rationale vs code
- `gcm.c:9-13` rejects table-driven GHASH because data-dependent timing leaks keys, but the
  AES under it (`crypto.c:178-195, 300-316`) uses S-box table lookups on key-dependent state
  and a conditional in `xtime` (209-211); AES is the same key's weakest point.
- `crypto.c:3-8` justifies the slow, readable AES with "a handshake that happens once when
  joining a network is a tenth of nothing"; AES now encrypts every TLS record via `gcm.c`.
- `tls.c:214-216` says a broken connection and a failed authentication "are not distinguished
  on purpose", but they get different error texts (219/223 vs 250).
- `tls.h:42` "Never empty after a false": `tls_send` returns false without calling `fail()`
  (`tls.c:835, 839`), so `http.c:115` can print "tls: no error" (or a stale reason).

### 10.13 WPA MIC over at most 256 bytes
`wpa.c:75-76`: `mic_of` silently truncates frames longer than 256 bytes to 256 before the HMAC,
both when signing and when checking. Legitimate longer EAPOL-Key frames (e.g. message 3 with
several KDEs) would fail; a 256-byte frame with appended bytes would verify with the extra
bytes unauthenticated. Latent -- no driver calls it.

### 10.14 Dead state and constants
`tls_t.handshake_done` (60, 823, 900) and `keys_are_app` (76, 819) are written, never read;
`HS_NEW_TICKET`, `HS_KEY_UPDATE` unused; `EAPOL_HEADER_LEN`, `TK_LEN` unused; `ec_base_x` and
all of `wpa.c` are used only by selftest; `tls_describe` always returns the same literal
(825).

### 10.15 Minor
- The Finished comparison is a plain `memcmp` (early exit, `tls.c:745`); impact is negligible
  (one attempt per handshake) but inconsistent with the constant-time compares elsewhere.
  `aes_unwrap_key`'s final check also exits early (`crypto.c:374-375`).
- `tls_connect(-1, …)` (as selftest does at `selftest.c:1748`) allocates ~66 KB of buffers for
  `nowhere` that are never freed.
- `SYS_TLS_STATUS` reports the machine-wide last error; `userland/term.c:1121-1123` calls
  `tls_why` after any `connect_tls` failure (including DNS/connect errors), so it can show a
  stale reason from an unrelated earlier handshake.
- Secrets and the ephemeral private key stay in the slot after `tls_close` (`tls.c:891-904`).

### 10.16 RSA-PSS assumes the modulus length is a multiple of 8 bits
`rsa.c:283-304` uses `emLen = n_len` and masks one top bit. For moduli whose bit length is not
≡ 0 mod 8 (emBits = modBits − 1 needs more masked bits, or emLen = n_len − 1), valid signatures
are rejected. Rare in practice (servers use 2048/3072/4096-bit keys).

### 10.17 Cross-area: socket slot not reserved before blocking
`syscall.c:754-767, 789-808`: `sock_take()` returns the first non-open slot, which is marked
open only after `tcp_open` (and `tls_connect`) return. Two overlapping connects could pick the
same `h`. (Owned by the syscall/network area; noted because it matters for §9 item 2.)

## 11. Open questions

1. **Timeouts inside syscalls on one CPU.** The syscall gate is an interrupt gate
   (`idt.c:63`, 0xEE) and neither the TLS nor the TCP wait loops re-enable interrupts, while
   `timer_ticks()` only advances in the timer IRQ (`timer.c:16-18, 56`). On a uniprocessor,
   can the 20 s `read_exact` deadline, `sys_recv`'s 4000 ms and `tcp_open`'s 6000 ms ever
   expire inside a syscall, or does a silent peer spin forever while holding the kernel lock?
   (On SMP, another CPU's ticks would advance the counter.) Needs confirmation from the
   interrupts/scheduler and network owners.
2. Can two `tls_connect` calls really interleave today (kernel shell `fetch` preempted +
   userland `connect_tls`), and is the kernel shell reachable while the desktop runs, or only
   over serial in tests?
3. Which PEM bundle (and `certifi` version/date) produced the current `roots.c`? Is the
   absence of GTS Root R2 intended?
4. Was lifting the single-secure-socket rule in `sys_connect_tls` intended to follow in the
   next commit? The userland comment (`fetch.h:454-458`) expects "the browser asking for a page
   and its pictures at once" at a higher layer.
5. Is fail-open date checking (`now == 0`) intended to remain, given that `rtc_read` fails only
   when the update-in-progress bit never clears?
6. Intended behaviour for very long certificate chains: more than 8 certificates are silently
   dropped (`tls.c:701`), and a Certificate message over 32 KB fails.
